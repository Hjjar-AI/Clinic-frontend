# GitHub automation

[Setup](setup.md) · [Verification](verification.md) · [Backend automation](../../backend/docs/automation.md) · [Executable bundles](../../backend/docs/bundles.md).

`.github/workflows/checks.yml` runs unit/component tests and a Vite production build on pushes, pull requests, manual dispatch and Mondays at 03:17 UTC. Windows 2022/Linux Ubuntu 24.04 x64 use Node 24.21.0 and pnpm 12.10.1, installing with `--frozen-lockfile`. Successful builds are downloadable artifacts retained for 14 days. No auto-fixing lint, lockfile edits or publishing occurs.

Component checks use the documented direct-Node Vitest fallback with `--configLoader runner`, caching disabled and isolated runner-temporary cache paths. This avoids relying on a shared local Vite module cache; package scripts remain unchanged.

`.github/workflows/browser.yml` is manual: choose **Actions → Browser checks (manual) → Run workflow** and supply the exact backend commit SHA. It checks out both repositories as siblings, installs backend/native dependencies and Playwright Chromium, and runs the existing desktop/tablet/mobile cases with disposable synthetic backend storage. Failed-run traces/screenshots are retained for seven days. This does not resume local browser work automatically or certify all visual/native printing behavior.

Both repositories are public; no custom checkout secret is needed. The selected backend revision must include its `.github/actions/native-dependencies` composite action. Both repositories' workflow changes must be pushed before using coordinated checks.

`.github/workflows/compatibility.yml` is a manual entry point for testing the selected frontend revision against an exact backend SHA. It reuses the browser workflow, including synthetic API-backed interactions and recorded source revisions. The backend has the corresponding entry point for an exact frontend SHA and calls a pinned, published frontend workflow definition. Compatibility/browser checks are not scheduled automatically and do not resume local browser work.

`.github/workflows/dependency-audit.yml` runs `pnpm audit --json` on package/lockfile/audit-workflow changes, manual dispatch and Mondays at 03:47 UTC. Reports include production and development dependencies, are retained for 14 days even when findings fail the job, and never apply fixes. Advisory-service/resolution failures also fail the job and must not be treated as a clean scan.

The backend's manual release workflow builds this frontend together with a backend executable for Windows/Linux, downloads/extracts the resulting archives on matching OS runners and checks their retained source revisions and runtime. Supply the frontend commit SHA there; frontend build artifacts alone are web assets, not executables. A separate manual workflow can prepare a draft GitHub Release from reverified archives and an existing matching tag; publishing and deployment remain manual.

## Workflow maintenance

Both repositories run `.github/workflows/workflow-validation.yml` on pushes, pull requests and manual dispatch. This Linux-only, read-only job has a five-minute limit. It downloads actionlint **1.7.7**, verifies the archive against an embedded SHA-256 before extraction, and validates workflow structure/expressions. CI-only PyYAML **6.0.3** and `.github/scripts/workflow_tools.py` check YAML duplicate keys, composite-action structure, immutable external references, helper syntax and embedded Python with AST; job Python is never executed by validation. Optional actionlint shellcheck/pyflakes integrations are disabled so validation has no implicit tool dependencies.

External action references, including composite actions and the backend's cross-repository browser workflow definition, use verified full commit SHAs with readable ref comments. `.github/dependabot.yml` checks only GitHub Actions weekly on Mondays at 06:17 UTC, grouping updates into one open reviewable PR per repository. No auto-merge or application dependency updates are configured. Review upstream changes before merging an action-pin update. The pinned browser workflow definition and the frontend/backend source SHAs passed into it are separate: selecting new source does not update the workflow definition. Refresh that pin through a reviewed change when adopting newer workflow behavior.

pnpm setup precedes setup-node's lockfile-keyed pnpm-store cache. Python install jobs cache pip downloads, keyed by the root and profile requirement files; the standalone validation job keys its cache by its own workflow containing the YAML-tool pin. These caches contain download data, not installed environments, `node_modules`, executables, clinic storage or isolated Vitest caches. Frozen installs and vulnerability scans still run; audit results are not cached.

Checkout steps immediately record actual commit SHAs, including frontend `main` resolved by automatic backend checks. Each runner job has an `always()` summary with OS, checked-out/requested revisions, major step outcomes and uploaded artifact IDs/links when available. Metadata reporting is inline and uses only standard-library Python so arbitrary selected source revisions do not need new helper files. Checkout failures report unavailable source revisions; missing upload outputs are not treated as available artifacts. Compatibility wrappers also report the called job result and requested source SHAs.

Checks, audits and validation cancel superseded automatic runs only within the same workflow/event/branch or PR. Scheduled/manual runs have unique run-ID groups, preventing replacement by automatic or other manual runs. Existing draft-release serialization is retained; browser runs and release jobs are outside automatic cancellation. No attestation, publishing, deployment or repository-setting changes are included.
